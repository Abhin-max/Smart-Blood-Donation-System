Architecture

Four structures, four specific jobs

Each one was chosen for a reason — nothing is used just to pad the requirement list.

vector<Donor>

Donor storage

The master record store, in the order donors were registered. Every donor's array position never changes once assigned.

Register → O(1) amortized
unordered_map<string, vector<int>>

Blood group index

Maps each blood group to the array positions of donors with that group, so a search only touches donors that could match.

Bucket lookup → O(1) avg, scan → O(k)
priority_queue<BloodRequest>

Blood request queue

A binary heap. "View Requests" always shows the most urgent request first, no matter what order they were added in.

Push → O(log n)
list<DonationRecord>

Donation history

Append-only log, always read front-to-back. A linked list skips the reallocation cost a vector pays as it grows.

Append → O(1)
Key design decision

Search by Donor ID is O(1) without a second hash map. IDs are assigned sequentially, and "Delete Donor" never physically removes a record — it just flags it as deleted ("soft delete"). That means donor ID N is always at vector position N‑1, forever. So ID lookup is direct array access, not a search at all.

Viva Preparation

      
Quick answers to have ready

    

    

    

      Why unordered_map instead of map?
      
map keeps keys sorted using a tree — O(log n). We never need sorted blood groups, so unordered_map's average O(1) hashing is the better fit.

    

    

      Why is ID search O(1) without a hash map?
      
Donor IDs are sequential and donors are soft-deleted, never physically removed — so donor ID N always sits at vector position N-1. Direct array access, no search needed.

    

    

      Why priority_queue for requests?
      
Emergency requests must be served by urgency, not arrival order. A binary heap gives O(log n) insert and always keeps the most urgent request accessible in O(1).

    

    

      Why doesn't Emergency Matching use the request queue?
      
They're deliberately separate: the queue is a prioritized record for tracking, while Emergency Matching is an immediate, on-the-spot lookup. Keeping them apart means each data structure has exactly one clear job.

    

    

      Why list for donation history?
      
History is append-only and read front-to-back, never randomly accessed — list avoids the reallocation cost a vector pays as it grows.
